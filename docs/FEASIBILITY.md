# Dataset extension: is 83 + 83 feasible by 22 November?

> **Update (10 November).** The extension was carried out: **40 + 40 pairs** are now analysed ([DATASET.md](DATASET.md), sections 7–8; [RESULTS.md](RESULTS.md)). 25 pairs meet the strict rule; 15 were added with relaxed rules (30–59 commits, or fewer than 2 % declared files) and are marked. Every candidate of the first search was reviewed, so going beyond 40 needs the wider search below. The analysis below is the assessment written before the extension.

The professor asked (9 November) to assess whether 83 matched pairs are feasible by 22 November and to agree on a smaller target if they are not. This document gives the numbers behind the assessment and a proposal.

## 1. What limits the number of pairs

| Step | Cost per pair | 83 pairs | Bottleneck? |
|---|---|---|---|
| Find AI-declared candidates | search runs once | see section 2 | **yes: number of eligible repositories** |
| Validate declarations by hand | about 10–15 min per AI repository | 14–21 h | **yes: manual work** |
| Choose a Pre-AI partner (size, stars, domain) | about 10 min (pool of 2,014 candidates already exists) | about 14 h | moderate |
| Scan 2 × 30 commits (SonarQube + Semgrep on the laptop) | 60 × 22 s ≈ 22 min (measured: 360 commits, mean 21.9 s) | about 30 h of laptop time | moderate: runs unattended |
| Ruff, tracking, validation, analysis, app | minutes | under 1 h | no: fully scripted |

Scanning and analysis scale without extra effort. The limits are **how many eligible AI-declared repositories exist** and **the manual validation**.

## 2. How many eligible AI-declared repositories the first search found

The first search (September; 15 phrases, at most 300 results per phrase) found 3,644 declaration hits in 1,636 repositories. After the automatic filters:

| Filter | Repositories |
|---|---:|
| Declaration rule met (≥ 2 declared files and ≥ 2 % of `.py` files) | 151 |
| … with ≥ 30 non-merge commits (enough for a shorter sample) | 63 |
| … with ≥ 60 non-merge commits (current rule, 30 sampled commits) | 45 |
| … with ≥ 100 non-merge commits | 31 |

Some of these will fail manual validation (in the first round, test strings and documentation that only *mention* an AI tool were rejected). With the current rules the first search supports **about 30–40 pairs**, not 83.

## 3. Wider search (ready to run)

[`scripts/find_candidates_wide.py`](../scripts/find_candidates_wide.py), started with [`run_wide_search.ps1`](../run_wide_search.ps1), widens the search while keeping the same evidence rule:

- 40 declaration phrases instead of 15 (e.g. "written with ChatGPT", "generated with Claude Code", "generated by Gemini", "AI-generated code"),
- every phrase query split into six file-size slices, so no query hits GitHub's 1,000-result cap, and up to 10 pages per slice (first search: 3 pages),
- commit-message declarations (`Co-Authored-By: Claude`, `Generated with Claude Code`, `Co-authored-by: Copilot`, …) searched month by month. These are a **different kind of evidence** (they declare the commit, not a source file) and are reported in a separate column and class, so the professor can decide whether to accept them,
- automatic pre-classification: **A** (declaration rule and ≥ 60 commits: check first), **B** (declaration rule, 30–59 commits), **C** (commit evidence only or < 2 files), **X** (rejected, with the reason).

It needs a GitHub token (entered when the script asks; it is never saved) and runs for 2–6 hours. It was written and checked here (dry run: 528 queries), but could not be run from this environment, because GitHub's search API needs the token on the laptop.

## 4. Proposal

| Option | Pairs | Feasible by 22 November? | Condition |
|---|---:|---|---|
| **Recommended** | **30 + 30** | Yes | Wider search gives about 40 class-A candidates (the first search alone already has 45 before manual checking). About 11 h of scanning and about 10 h of manual work. |
| Stretch | 40–50 + 40–50 | Possibly | Also accept class B (30–59 commits) with 20 sampled commits per repository instead of 30. |
| Full | 83 + 83 | No | Needs about 120 class-A candidates (not available in the first search), about 30 h of scanning and 30–35 h of manual validation. Realistic only in December, and only if the wider search finds enough repositories. |

With 30 pairs, the repository-level tests (the main result) can detect large effects after correction (the smallest exact p-value for 30 vs 30 is far below the Holm threshold), which is not possible with 5 pairs.

**Questions for the professor**

1. Is 30 + 30 by 22 November an acceptable target, with 83 as a later extension?
2. Should commit-message declarations (e.g. `Co-Authored-By: Claude`) count as AI declarations, or only declarations inside source files?
3. For repositories with 30–59 commits, is a sample of 20 analysed commits acceptable?

## 5. Plan once the target is agreed

1. Run `run_wide_search.ps1` (2–6 h, unattended).
2. Validate class-A candidates by hand, in order; record each decision in `data/candidates/wide/ai_candidates_wide.csv` (column to add: `manual_decision`).
3. Match each accepted repository with a Pre-AI partner from `data/candidates/preai_pool_stratified.csv` (same criteria as [DATASET.md](DATASET.md), section 4).
4. Scan with `scan_repos.py` (about 22 min per pair, unattended; can run overnight), then `run_ruff.py` and `run_pipeline.ps1`.
5. The AI-declaration windows are found automatically (`git log -G`), as for the current five pairs.
